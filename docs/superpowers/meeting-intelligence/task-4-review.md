# Task 4 review: fixed-scope grounded QA and history

## Verdicts

- **Spec compliance: CHANGES REQUIRED.** Optional Workspace scope, unavailable-scope publication, clarification/follow-up context, and historical source hints do not meet the approved contract.
- **Task quality: CHANGES REQUIRED.** The immutable scopes, owner checks, citation snapshots, exact ID/quote checks, fresh retrieval, controlled model failures, and transactional publication comparison are useful foundations. The concrete service bugs below remain acceptance blockers.

## Scope and evidence

Read `task-4-brief.md` first, then `task-4-report.md`, `task-4-diff.txt`, all three current implementation modules, and their two test modules. Checked the relevant approved PRD requirements and actual Task 3 indexer/source interfaces. No implementation edits or subagents were used. This report is the only file written.

Accepted the supplied verification: 2 focused suites / 12 tests and 9 meeting suites / 96 tests passed; scoped lint and formatting passed. Those suites were not rerun. Additional read-only in-memory Node probes targeted uncovered service behavior; these are not production or provider integration verification.

## Findings

1. **[P1] Reject unavailable meetings at the baseline and publication snapshots.** `server/modules/meetings/qa.js:311-313` checks availability in one query, then builds a separate baseline snapshot whose meeting read explicitly bypasses availability (`qa.js:123-124`). Publication at `qa.js:406-408` only compares the two digests. If a meeting transitions from AVAILABLE to INDEXING between the initial check and baseline read, both snapshots contain the same unavailable state and the successful result is published. With the actual `createIndexer`, the unavailable meeting is excluded from retrieval; any Workspace evidence can therefore produce an ANSWERED result that silently omits that selected meeting. A targeted reproduction returned `{status:"ANSWERED",meetingState:"INDEXING",published:1,usingActualIndexer:true}`. With no Workspace evidence the same hole can publish AWAITING_SOURCES instead of blocking the unavailable scope. Validate all selected meetings' existence/nondeleted/AVAILABLE state from the baseline and again inside publication, independently of snapshot equality. Keep the deliberately permissive snapshot read for history. PRD REQ-QA-001 requires any selected unavailable meeting to block continued questions and reanswers.

2. **[P2] Allow the default empty Workspace set.** `server/modules/meetings/qa.js:212` calls `normalizeIds` with its default minimum of one (`qa.js:22-27`). Both omitted `workspaceIds` and `workspaceIds: []` throw `INVALID_WORKSPACE_SCOPE`. This makes the normal meeting-only conversation impossible, contrary to PRD line 211: every new conversation defaults to no enterprise knowledge base; accessible Workspaces are optional explicit additions. Default omitted scope to `[]` and validate the Workspace array with `min: 0`, retaining positive-ID/duplicate/access checks for selected values. The report's claim that at least one Workspace is required should be corrected. Both rejected inputs were reproduced.

3. **[P2] Supply conversation references and clarified conditions to fresh retrieval.** `server/modules/meetings/qa.js:300-310` fetches the previous answer solely to verify its conversation and then discards it. Retrieval receives only the latest question (`qa.js:313` and `qa.js:320-324`); the model prompt also receives no previous question or previous missing-information request (`qa.js:373-380`, `grounding.js:17-25`). An ordinary follow-up such as “What about that warehouse?” loses its antecedent. A clarification such as “Warehouse B” is passed to the model only after retrieval; if searching the ambiguous question yields no evidence, the service skips the model and returns AWAITING_SOURCES despite the clarified query having usable sources. Build bounded conversation-reference context from the linked question/missing-information request and include the clarified conditions in the fresh retrieval query. Keep old answer text/citations explicitly non-evidence. A probe confirmed that the previous question was absent from the prompt and both retrieval adapters received only the ambiguous latest question.

4. **[P2] Preserve the clarification input as part of the answer request history.** `server/modules/meetings/qa.js:434-445` stores `question` and linkage but never stores `input.clarification`; the stale-record path (`qa.js:409-421`) also drops it. History therefore cannot recover the actual conditions under which the answer was generated, and a later manual reanswer linked to that row cannot recover those conditions. The approved data contract includes the question's clarification or missing information (PRD line 276); `missingInfo` records the model's requested information, not the user's supplied conditions. Persist a validated clarification/request-context field without overwriting the old answer; expose it with the saved row and use it only as untrusted conversation data in follow-ups/reanswers.

5. **[P2] Separate cited-source invalidation from successfully indexed new information.** `server/modules/meetings/qa.js:138-157` snapshots every nondeleted source, including PENDING/PROCESSING/FAILED sources. `qa.js:195-202` then marks any newly present source as `newSources`, and any removed/changed source as `stale` even when that source was never cited. The history callers (`qa.js:257-261`, `qa.js:281-285`) never pass citation identity into comparison. A failed supplemental-file insertion was reproduced as `{stale:false,newSources:true}`; deleting an uncited source was reproduced as `{stale:true,newSources:false}`. PRD lines 171 and 231-232 distinguish referenced-source changes from new retrievable information and expressly exclude parse/index failures from the new-information hint. Keep the broad manifest for in-flight publication invalidation, but compute history hints separately: compare referenced source identities/revisions for citation staleness; require successfully indexed, currently retrievable additions/revisions for new-information hints. Scope-unavailable state should remain an independent reason to block new asks. Do not repoint old citation snapshots to a reuploaded source ID.

## Correct behavior observed and boundaries

- The service stores fixed meeting/Workspace sets and checks owner/access on conversation operations; prior answer rows are never used as fresh evidence. Reanswer produces a new linked row.
- Meeting source addition/deletion/revision after the baseline is captured is detected by the broad transactional manifest comparison, including additions without a generation increment. Historical citation text survives source deletion and unavailable meetings.
- Grounding validates current evidence IDs and exact nonempty quote substrings, permits cited partial pending answers, and separates model runtime failure/partial output from missing sources. The prompt requests parallel conflict presentation, distinct discussion/decision handling, and an untrusted-data boundary.
- These structural checks do **not** prove semantic entailment, detect every uncited assertion, or prove model compliance with conflict/approval semantics. Real-provider acceptance cases for fabricated facts, deleted-source use, unsupported confidence, and proposals portrayed as approved decisions remain the release gate.
- Task 5 provider/authenticated Workspace/runtime wiring and original-file routes, and Task 6 UI, were not treated as Task 4 defects. No live API/provider, Linux deployment, original-file opening, or production performance verification was performed.
