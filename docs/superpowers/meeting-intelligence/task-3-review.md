# Task 3 review

## Verdicts

- **Spec compliance: changes required.** The located index can lose or misattribute source chunks, and source/index workers can publish an incomplete current generation. The delete API also accepts imported summary/transcript sources even though the intended delete/reupload path is for draft supplements.
- **Code quality: changes required.** The parser and persistence boundaries are mostly explicit, and the reported focused tests cover several core paths, but the ownership and concurrency invariants are not enforced at publication. The import transaction can also leave attachment files behind after a later rollback.

## Actionable findings

1. **[P1] Reindex assigns later chunks to the wrong source, or drops them.** `server/modules/meetings/indexer.js:245-254` builds `ownerIds` per *segment* but indexes it with `cursor`, which advances per *chunk*. If a first segment splits into two chunks, the next segment looks up `ownerIds[2]` instead of `ownerIds[1]`. With two segments it becomes `undefined` and is skipped by `activeIds.has` at lines 271-273; with three or more, it can attribute the next segment to a different source. A normal long paragraph followed by another paragraph triggers this. It loses evidence and can produce a citation naming the wrong source. Keep a segment index separate from the prepared-chunk cursor, and add a reindex regression with a long first segment and a second source.

2. **[P1] Reindex can erase a source that finished parsing during embedding.** `server/modules/meetings/indexer.js:213-215` captures successful sources before `await prepare` at line 244. The publish transaction at lines 265-294 only checks the meeting generation, then deletes *all* meeting chunks and inserts chunks from the earlier capture; it does not compare the current successful-source set to the captured set. Upload/parse does not increment generation (`server/modules/meetings/sources.js:180-218`). If a new source becomes `SUCCESS` while a deletion or revision reindex is embedding, its newly written chunks are erased, yet the meeting is published as `AVAILABLE` with that source still `SUCCESS`. Search silently omits it and approval can pass. Abort/retry publication when the source set or source revisions changed, or serialize the two publishers.

3. **[P1] An expired parse worker can overwrite the result of its replacement.** `server/modules/meetings/sources.js:410-425` and `:489-509` validate source hash and meeting generation, but neither path validates `job.leaseOwner`, job status, or whether the source has already succeeded. The shared runner may reclaim an expired `PROCESSING` job (`server/modules/meetings/jobs.js:61-85`). If worker B reclaims and indexes the source while worker A is stalled in OCR or embedding, A's later failure sets `parseStatus: FAILED` after B's success. The meeting may remain `AVAILABLE`, but search filters that source out and approval blocks. Tie source publication/failure to the current lease and avoid changing an already successful source from a stale attempt.

4. **[P2] A meeting revision can strand a pending source permanently.** A parse job that started before a summary/transcript revision returns `{stale:true}` when the meeting generation changes (`server/modules/meetings/sources.js:417-426`). The source remains `PENDING`; the runner marks that job `SUCCESS`, and no replacement parse job is queued. Reindex selects only `SUCCESS` sources (`server/modules/meetings/indexer.js:213-215`), so the pending source never gets indexed and `approve` rejects it indefinitely (`server/modules/meetings/meetingService.js:215-223`). Requeue or reprocess the active source for the new generation before treating the job as complete.

5. **[P2] Removing an imported summary or transcript bypasses the supplement-only deletion rule.** `server/modules/meetings/sources.js:287-317` rejects only `TENCENT_ORIGINAL`. A caller can remove active `SUMMARY` or `TRANSCRIPT` sources in a draft, despite those being Tencent-imported material; the separate meeting `summary`/`transcript` fields remain populated while reindex drops their evidence. Restrict deletion to `SUPPLEMENT_FILE` and `SUPPLEMENT_TEXT`, or define and implement a distinct imported-content removal operation that also updates meeting fields and coverage.

6. **[P2] Import rollback after source commit can orphan stored attachment files.** `server/modules/meetings/sources.js:693-770` writes files before the caller's transaction commits and removes them only if an error occurs *inside* `commitImport`. The importer then calls `completeJob` in the same transaction (`server/modules/meetings/importer.js:539-549`), which can throw on a lost lease (`:118-128`) and roll the database transaction back. Files written by the successful `commitImport` remain unreferenced. The selected content is not queryable, so the content-exposure guarantee holds, but failed/retried imports can accumulate private files. Stage files outside the final store or clean them when the outer transaction fails.

7. **[P2] Remote OCR validation does not enforce document-specific provenance.** `server/modules/meetings/parser.js:57-99` accepts an `image` location with no identifying field and accepts `paragraph` for a scanned PDF; `parseRemote` at lines 287-297 applies that generic validator without checking the uploaded format. A service response such as `{text:"...",location:{type:"paragraph",paragraph:0}}` for a multi-page scanned PDF is accepted and indexed as though it has an exact locator. Require a page for scanned PDF segments and an image/slide locator that identifies the original asset, with a response test for missing or mismatched location.

## Checks and limits

The reviewed diff and the source files support the findings above. The Task 3 report records 25 focused tests, 67 associated tests, and scoped lint/format checks as passing; I did not rerun them. I did not run a native/OCR service, embedding provider, live Tencent API, or production performance check. Those remain release gates.
